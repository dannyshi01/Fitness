## 01 背景與問題

使用者(同時也是唯一使用者)有規律健身習慣,但長期有兩個痛點:

- **到健身房沒有計畫、常常亂練** —— 缺一份「今天該練什麼」的菜單。
- **看到好動作卻留不住、也難歸類** —— 在 IG 看到影片、上實體課學到的動作,當下覺得好,事後卻散落各處、想不起來,動作一多更不知道怎麼分類收納。

市面上的健身 App 多半綁定自家動作庫、以「課表訂閱」或「社群」為核心,無法輕鬆收錄「我自己從各處蒐集來的動作 + 教練口述重點 + 原始影片連結」。因此需要一個**以個人動作庫為核心、收錄零摩擦、分類有彈性**的輕量工具。

## 02 目標與非目標

**目標 Goals**
- 快速收錄一個動作(名稱 + 一個標籤即可存),降低「看到好東西想記下來」的門檻。
- 動作可帶**來源連結、教練提示、示範圖片**,日後一鍵回看原影片。
- 用貼近自己思維的分類(部位 + 功能性)組織,並能收合瀏覽、搜尋。
- 把動作組成**依訓練日的菜單**,到現場照做。
- 最終能**跨裝置**(手機記、電腦看),資料不遺失。

**非目標 Non-Goals**
- 不做社群、分享排行、追蹤別人。
- 不做多人 / 教練帶學員(初期單一使用者)。
- 不自建龐大內建動作資料庫。
- 不做飲食、體重、身體數據追蹤(至少初期)。
- 不做原生 App 上架(以網頁 + 加到主畫面替代)。

## 03 使用者與情境

**主要使用者:** 有健身習慣、會主動蒐集動作與知識的個人。非工程背景,重視「快、順手、資料是自己的」。

**關鍵情境**
- **滑到好動作(捷運上):** 複製 IG 連結 → 開工具 → ＋ 新增 → 貼連結、選部位、存。10 秒完成。
- **上完實體課(課後):** 趁記得,新增動作並把教練口述重點打進筆記。
- **排課表(週末):** 建立「推日 / 拉日 / 腿日」菜單,從動作庫勾選動作、填組數次數。
- **健身房執行(訓練中):** 手機打開菜單照做;想不起動作細節時點進動作看說明與影片。

## 04 產品概念:三大支柱

- **📚 動作庫** — 個人動作資料庫。依部位/功能分類收合,點動作看說明、教練提示與來源影片。收錄零摩擦。
- **📋 菜單** — 依訓練日組成的課表,從動作庫挑動作 + 組數次數,到現場照著做。
- **📖 框架** — 依身體區域的動作框架(退階→原始→進階),當「今天該練哪個階段」的導覽。

## 05 功能需求

**已完成(Prototype)**

| 功能 | 說明 |
|---|---|
| 動作庫收合清單 | 依 胸/背/腿/臀/肩/核心 + 爆發跳躍/腳踝穩定/重心轉移… 分組,預設收合,展開看動作。 |
| 動作詳情 | 點動作看示範圖、分類/器材、來源影片按鈕、完整教練提示;可編輯/刪除。 |
| 快速新增 | 只填名稱即可存,其餘皆選填。 |
| 圖片 | 上傳自動壓縮成縮圖(最長邊 720px)。 |
| 菜單 | 建立訓練日菜單,勾選動作 + 組數次數。 |
| 框架參考頁 | 10 區域 × 目標肌肉/常見代償/退階·原始·進階。 |
| 搜尋 / 備份 | 跨分類搜尋(含筆記);JSON 匯出匯入。 |

**規劃中(見 §07 Roadmap)**
- **跨裝置同步 + 雲端圖片儲存**(最高優先的下一步)。
- **訓練紀錄:** 每次實際重量/次數的 log 與歷史。
- **菜單體驗:** 複製菜單當範本、動作詳情頁一鍵加入某菜單、組間休息計時。
- **框架↔動作連動:** 框架的動作可連到動作庫實際項目。
- **智慧建議:** 依部位/框架推薦、進退階提示、簡單統計圖表。

## 06 資料模型

| 實體 | 欄位 |
|---|---|
| Exercise 動作 | `id, name, cats[], equip, source, sourceUrl, imageData, notes, createdAt` |
| Menu 菜單 | `id, name, notes, items[{exId, sets, reps}], createdAt` |
| Framework 框架 | 唯讀常數:`zone, main, muscle, comp, regress, base, advance` |
| (未來) Log 紀錄 | `id, exId, date, sets[{weight, reps}], note` |

目前儲存於瀏覽器 `localStorage`(key `fitness_data_v2`),讀寫集中在 `load()` / `save()` 兩個函式 —— 刻意設計,未來換成雲端只需改這兩處。

## 07 Roadmap 路線圖

### PHASE 0 · DONE — 原型驗證(現況)
單檔 HTML + 原生 JS,資料存 localStorage。動作庫、菜單、框架、圖片、搜尋、備份皆可用,並以預覽連結在手機試用。
目標:確認資訊架構與操作流程貼合實際使用。

### PHASE 1 — 正式上線(單機版)(下一步)
- 部署到 **Cloudflare Pages**(repo 保持私有、免費、push 自動更新)。
- 加到手機主畫面像 App;確認離線可用。
- **圖片儲存改用 IndexedDB**,突破 localStorage 約 5MB 上限,支援大量示範圖。
- 細節打磨:分組順序、詳情頁排版、預設動作內容校對。

### PHASE 2 — 跨裝置同步 + 雲端圖片(核心升級)
- **後端方案:** Cloudflare(D1 資料庫 + R2 圖片儲存 + Access/Workers 登入),或 Supabase。同平台可從 Pages 平滑升級。
- 單一 Email 登入(簡單但真正安全)。
- 把 `load()`/`save()` 接到雲端 API;保留離線快取與衝突處理策略。
- 驗收:兩裝置資料即時一致、圖片正常同步。

### PHASE 3 — 訓練體驗增強(留存驅動)
- **訓練紀錄:** 執行菜單時記錄實際重量/次數,累積歷史。
- **菜單範本:** 複製上週菜單改成本週。
- **動作 → 菜單:** 在動作詳情頁一鍵加入指定菜單。
- **框架連動:** 框架動作連到動作庫實際項目。
- 組間休息計時器。

### PHASE 4 — 智慧化(探索・未來)
- 依部位/框架自動推薦動作、平衡訓練分佈。
- 進退階建議(依框架的 退階→進階)。
- 訓練量與進步的統計圖表。
- 貼上 IG/YT 連結時自動抓標題/縮圖。

## 08 技術架構路線

| 階段 | 前端 | 資料 / 圖片 | 部署 |
|---|---|---|---|
| P0–P1 | 單檔 HTML + 原生 JS | localStorage → IndexedDB(本機) | Cloudflare Pages |
| P2+ | 同前(必要時再模組化) | Cloudflare D1(SQL)+ R2(圖片)或 Supabase | Pages + Workers |

原則:**能不加複雜度就不加**。維持純前端、無 build、任何 AI 工具都好接手;資料層集中,升級時面積最小。

## 09 成功指標

個人工具,指標以「真的持續用」為核心:
- **持續使用:** 每週至少開啟並照菜單訓練 1 次以上。
- **收錄行為:** 看到好動作能在 30 秒內收進庫。
- **取代舊習慣:** 不再「到健身房才想今天練什麼」;動作不再散落各處。
- **資料留存:** 跨裝置後,零資料遺失。

## 10 風險與未決事項

**Open Questions**
- P2 後端選 **Cloudflare(D1+R2)還是 Supabase**?(傾向 Cloudflare:同平台、R2 無流量費)
- 離線編輯 + 雲端同步的**衝突處理**策略(單人多裝置,衝突機率低但需定義)。
- 影片「內嵌播放」還是維持「開連結」?(IG 內嵌限制多,傾向開連結)。
- 是否需要簡單的訓練「打卡」以支撐 §09 使用指標?

**Risks**
- **資料遺失:** 單機階段清瀏覽器即全失 → 以 JSON 匯出備份緩解,P2 上雲根治。
- **範圍蔓延:** 個人工具易越加越多 → 以本 PRD 的 Non-Goals 守住。
- **免費額度:** Cloudflare 個人用充足,僅極端爆量才需付費(非預期情境)。
